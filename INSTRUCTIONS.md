# INSTRUCTIONS — Як користуватися пайплайном a11y-audit-pipeline

Покрокова інструкція запуску пайплайну комплексної перевірки доступності (WCAG 2.2 AA). Пайплайн **тільки перевіряє та звітує** — нічого не виправляє автоматично.

## Передумови

- VS Code із AI-асистентом та підтримкою MCP-серверів (`.vscode/mcp.json`), а також інструкціями агентів (`agents/`) та скілів (`skills/`).
- Ціль аудиту: локальний каталог, репозиторій GitLab або GitHub, і/або URL; документи (.docx/.xlsx/.pptx/.pdf/.epub); markdown (.md).
- Встановлене ПЗ та налаштоване середовище — див. розділ «Встановлення ПЗ» нижче.

## Встановлення ПЗ

Виконати ОДИН раз перед першим запуском. Команди наведені для Windows (PowerShell).

### 1. Node.js >= 22.19 (обовʼязково)

MCP-сервери та сканери (`tools/`) працюють на Node.js. Мінімальна версія — **22.19** (вимога Lighthouse 13.x).

- Завантаж інсталятор з <https://nodejs.org/> і встанови.
- Перевірка:
  ```powershell
  node --version   # очікується v22.19+
  npm --version
  ```
- Якщо встановлено менеджер версій (fnm/nvm), переконайся, що активна сумісна версія: `fnm current`.

### 2. Стандартний відкритий npm-реєстр

Усі інструменти (`tools/package.json`) та MCP-сервери встановлюються зі стандартного відкритого реєстру npm (`https://registry.npmjs.org/`):
```powershell
npm config get registry   # має бути https://registry.npmjs.org/
```
Якщо раніше було налаштовано інший реєстр, скинь його на стандартний:
```powershell
npm config set registry https://registry.npmjs.org/
```

### 3. MCP-сервери

Workspace-конфіг `.vscode/mcp.json` локальний (ігнорується git) і мержиться з твоїми глобальними налаштуваннями MCP у VS Code. Шаблон — `docs/mcp.example.json`: скопіюй його у `.vscode/mcp.json` і заміни `<роль>` (та за потреби `<GITLAB_TOKEN>` або `<GITHUB_TOKEN>`). Шляхи в шаблоні відносні до кореня проєкту (робоча тека workspace-сервера); для глобального конфігу потрібні абсолютні шляхи.

| MCP | Пакет (npm) | Етапи | Авторизація |
|-----|-------------|-------|-------------|
| Playwright MCP | `@playwright/mcp` ([GitHub](https://github.com/microsoft/playwright-mcp)) | 2, 3, 4, 5 (опційно) | для цілі за логіном — `--isolated --storage-state` |
| GitLab MCP | `@modelcontextprotocol/server-gitlab` ([GitHub](https://github.com/modelcontextprotocol/servers)) | 1, 5 (лише `gitlab_read`) | `GITLAB_PERSONAL_ACCESS_TOKEN` у `env` |
| GitHub MCP | `@modelcontextprotocol/server-github` ([GitHub](https://github.com/modelcontextprotocol/servers)) | 1, 5 (лише читальні дії) | `GITHUB_PERSONAL_ACCESS_TOKEN` у `env` |

Обовʼязкові аргументи Playwright MCP:

| Аргумент | Навіщо |
|----------|--------|
| `--isolated` | профіль браузера в памʼяті; стан сесії не накопичується між запусками |
| `--storage-state "auth/playwright/.auth/<роль>.json"` | авторизована сесія з механізму `auth/` (працює лише разом з `--isolated`) |
| `--output-dir "output/runtime/mcp"` | снапшоти/скріншоти MCP пишуться в `output/`, а не в корінь проєкту |
| `--output-mode file` | великі снапшоти зберігаються у файли, а не в контекст чату |

Заборонено: `--save-session` (зберігає сесію у файл поза `auth/`).

Окремо встановлювати MCP-сервери не треба — `npx` підтягне пакети зі стандартного реєстру npm при першому запуску. Після зміни `mcp.json` зроби reconnect сервера в панелі MCP.

### 4. Браузери Playwright

Ставляться при встановленні Playwright (`npx --prefix tools playwright install chromium`) або автоматично при першому запуску Playwright MCP. Перший запуск може зайняти більше часу через завантаження браузерів.

### 5. Інструменти пайплайну `tools/` (обовʼязково для етапів 3–4 і стану)

Тека `tools/` містить локальні інструменти з закріпленими версіями (`tools/package.json`, встановлюються зі стандартного реєстру `https://registry.npmjs.org/`):

| Залежність | Версія | Для чого |
|------------|--------|----------|
| `axe-core` | 4.14.0 | етап 3: ін'єкція на базовому стані й попапах |
| `lighthouse` | 13.6.0 | етап 4: accessibility category на авторизованій сесії |
| `playwright` | 1.62.0 | драйвер браузера для сканерів, crawler-а і `auth-check` |
| `puppeteer-core` | 25.16.0 | етап 4: підключення Lighthouse user flow до браузера (та сама версія, що в залежностях Lighthouse) |

Встановлення (один раз і після оновлення `tools/package.json`):
```powershell
npm run setup:tools          # або npm install --prefix tools
npm ls --prefix tools        # усі залежності без помилок
npm test                     # або node --test tools/tests/ — самоперевірка інструментів
```

Скрипти:

| Скрипт | Призначення |
|--------|-------------|
| `node tools/pipeline-state.mjs <команда>` | єдиний спосіб змінювати `output/pipeline-state.json` і `output/pipeline-journal.md` (`init`, `stage`, `phase`, `journal`, `finish`, `archive`, `validate`, `show`) |
| `node tools/auth-login.mjs --role <роль> --url <URL>` | ручна авторизація людини у відкритому вікні браузера зі збереженням лише отриманого `storageState` у `auth/playwright/.auth/<роль>.json` |
| `node tools/auth-check.mjs --role <роль> --url <URL>` | перевірка, що storageState ролі існує й не прострочений (коди виходу: 0 valid, 3 missing, 4 expired, 5 error) |
| `node tools/popup-crawler.mjs --url <URL> --role <роль>` | детермінований обхід попапів у межах модуля → `output/runtime/02/states.json` (стани, out-of-module, небезпечні елементи, Escape/фокус) |
| `node tools/axe-run.mjs --url <URL> --role <роль> --states output/runtime/02/states.json` | axe-core на кожному стані → `output/runtime/03/<id>.json`, `output/scan-axe.json` |
| `node tools/lh-run.mjs --url <URL> --role <роль> --flow --states output/runtime/02/states.json` | Lighthouse user flow (navigation + snapshot) → `output/runtime/04/<id>.json`, `output/scan-lighthouse.json` |
| `node tools/verify-run.mjs [--dir output\|result_history/Pipeline_<мітка>]` | етап 11: трасування 02..07 → 08 → 10, weighted score, BUG → FINDING, схема стану, секрети, `git status` проти базової лінії → `output/runtime/11/verify.json` (код 1 = FAILED) |

Спільні коди виходу runtime-скриптів: 0 успіх, 3 немає стану сесії, 4 сесія недійсна (редірект на логін), 5 помилка, 6 сторінка поза модулем. Кожен клік проходить класифікатор `tools/action-policy.json`; небезпечні елементи натискаються лише за записом людини в `output/runtime/approvals.json`. Allowlist модуля — `tools/action-policy.<module>.json` (змінює людина).

Глобальні `npx @axe-core/cli` / `npx lighthouse` не використовуються: CLI не бачить авторизованої сесії та попапів і не має закріпленої версії. Markdownlint для етапу 7 не обовʼязковий — етап 7 читає файли безпосередньо.

### 6. Авторизація для сторінок за логіном (якщо ціль за автентифікацією)

Якщо ціль аудиту доступна лише після логіну, потрібен збережений стан сесії (**storageState**), який передається Playwright MCP через `--storage-state`.

Детальний порядок (ручний вхід у браузері, збереження сесії, безпека) описано в окремому файлі:

- **`auth/AUTH-SETUP.md`** — повна інструкція ручної авторизації та збереження сесії.
- Збережені стани сесій кладуться в `auth/playwright/.auth/<роль>.json` і **ігноруються git** (`auth/**/*.json` у `.gitignore`) — це секрет.

Коротко: авторизація виконується людиною вручну у відкритому вікні браузера командою:
```powershell
node tools/auth-login.mjs --role <роль> --url "<URL цілі>"
```
Скрипт не приймає і не зберігає паролів чи ключів — після того як ти увійдеш у браузері й відкриється цільова сторінка, він збереже лише отриманий стан сесії (`storageState`) у `auth/playwright/.auth/<роль>.json`. Далі Playwright MCP отримує шлях до цього файлу через `--isolated --storage-state`.

Стан сесії живе обмежений час. Перед етапом 1 і перед кожним runtime-етапом (2–4) перевір його:
```powershell
node tools/auth-check.mjs --role <роль> --url "<URL цілі>"
```
- `valid` (код 0) — можна запускати runtime-етапи;
- `missing` (3) або `expired` (4) — онови сесію вручну через браузер (`node tools/auth-login.mjs --role <роль> --url "<URL цілі>"`) і зроби reconnect Playwright MCP у VS Code;
- `error` (5) — проблема мережі/браузера, подивись повідомлення.

Стан сесії НІКОЛИ не зберігається в `output/` чи `result_history/`: `archive` виключає такі файли з архіву, а `verify-run` перевіряє їх відсутність.

## Перший запуск (checklist)

Перед першим повним прогоном пайплайну переконайся:

1. **Node.js**: `node --version` показує v22.19 або новіше.
2. **Реєстр npm**: `npm config get registry` вказує на стандартний відкритий реєстр `https://registry.npmjs.org/`.
3. **Інструменти**: виконано `npm run setup:tools` (`npm install --prefix tools`), `npm ls --prefix tools` без помилок, `npm test` (`node --test tools/tests/`) — усі тести pass.
4. **MCP-конфіг**: `.vscode/mcp.json` створено з `docs/mcp.example.json`; Playwright MCP (`@playwright/mcp`) має `--isolated`, `--storage-state`, `--output-dir`, `--output-mode file` і НЕ має `--save-session`.
5. **MCP підключені**: переконайся в VS Code, що сервери `playwright-mcp` і (за потреби) `gitlab` або `github` запущені (running/connected). Якщо ні — перезапусти сервер (restart/reconnect).
6. **Авторизація** (якщо ціль за логіном): `node tools/auth-check.mjs --role <роль> --url <URL>` повертає `valid`.
7. **Перший виклик Playwright MCP**: перший `browser_navigate`/`browser_snapshot` може завантажувати браузери — це нормально, зачекай завершення.
8. **Ціль готова**: для runtime-сканів піднятий dev-сервер або доступний URL; для GitLab/GitHub-цілі — відомі репозиторій і гілка.

Після цього переходь до «Крок 1».

### Типові проблеми першого запуску

| Симптом | Причина | Що зробити |
|---------|---------|-----------|
| `npm ERR! 404` під час встановлення | налаштований нестандартний/недоступний реєстр npm | виконай `npm config set registry https://registry.npmjs.org/` |
| MCP-сервер не піднімається / timeout | Node.js старіший за 22.19 або немає доступу до npm | перевір `node --version` та підключення до мережі |
| Runtime-етапи бачать сторінку логіну | storageState прострочений | `node tools/auth-login.mjs --role <роль> --url "<URL>"` → увійти в браузері → reconnect Playwright MCP |
| `npm install --prefix tools`: `EBADENGINE` | Node.js старіший за 22.19 | онови Node.js (крок 1) |
| Playwright: довго «висить» на першому виклику | завантаження браузерів | зачекай або виконай `npx --prefix tools playwright install chromium` |
| Етапи 2–4 пишуть «URL не наданий» | не вказано URL / не піднято сервер | вкажи URL у Discovery або підніми dev-сервер |

## Крок 1. Визначення вхідних параметрів

## Крок 2. Запуск

### Повний пайплайн
Активуй оркестратор через контекстний ключ у чаті:
```
#A11y Audit Pipeline Orchestrator
```
і вкажи ціль аудиту. Оркестратор:
1. створить `output/pipeline-state.json` та `output/pipeline-journal.md` через `node tools/pipeline-state.mjs init` (якщо в `output/` лишились файли незаархівованого запуску, він спершу запропонує архівувати їх або очистити через `init --clean`);
2. поетапно активуватиме агентів 1→11;
3. зупинятиметься для твого підтвердження після кожного етапу.

### Окремий етап
Можна активувати конкретний агент, напр.:
```
#A11y Web Review
```
Вхідні дані беруться з відповідних `output/NN-*.md`. Переконайся, що попередні етапи вже сформували свої файли.

## Крок 3. Що робити на кожній фазі

Пайплайн виконується фазами: **A** (етап 1) → **B** (паралельно етапи 2–7) → **C** (етапи 8 → 9\* → 10; \* опційний) → **D** (етап 11).

### Фаза A — етап 1 (Discovery)
Виконується одразу. Після нього оркестратор запитає **«Так / Ні / Зупинити»**.

### Фаза B — паралельні етапи 2, 3, 4, 5, 6, 7
1. Спершу оркестратор окремо по кожному етапу запитає **«Виконати чи пропустити?»** (напр., пропусти етап 6, якщо немає документів). Етапи без контенту (або без URL для 2–4) пропускаються автоматично.
2. Обрані «Виконати» запускаються **разом** (паралельно). Кожен пише свій `output/NN-*.md`.
3. Етапи 2–4 (runtime: симуляція, axe-core, Lighthouse) працюють лише в межах модуля (останнє слово хеш-шляху URL) і відкривають усі доступні попапи. Якщо вони зустрінуть небезпечний елемент ("Підписати", "Надіслати", "Видалити", "Підтвердити" тощо) — вони НЕ натиснуть його автоматично, а оркестратор поставить тобі окреме явне питання по кожному такому елементу: **«Натиснути цей елемент? (Так, натиснути / Ні, пропустити)»**.
4. Після завершення ВСІЄЇ групи буде **одне спільне ревʼю** — зведений підсумок і один запит **«Так / Ні / Зупинити»**:
   - **Так** — прийняти всю фазу, перейти до фази C.
   - **Ні** — вкажи, який саме етап переробити; після переробки знову спільне ревʼю.
   - **Зупинити** — зупинити пайплайн (стан збережеться).
5. Якщо якийсь етап впав з помилкою (`failed`), інші не зупиняються. Оркестратор покаже успішні й той, що впав, і запитає, продовжити з наявним чи зупинитись.

### Фази C і D — послідовні етапи 8, 9, 10, 11
Як у класичному режимі: питання «Виконати/Пропустити» (крім обовʼязкового етапу 11) і підтвердження «Так/Ні/Зупинити» після кожного етапу.

**Етап 9 опційний**:
- **Етап 9 (Bug Reports).** Агент перетворює консолідовані знахідки на готові структуровані баг-репорти (critical/serious по одному, moderate/minor групами за критерієм WCAG) і експортує їх у файл `output/09-bug-reports.md`. Жодних записів у зовнішні системи не виконується.

Короткий огляд етапів:
1. **Discovery** (фаза A) — визначає scope, роль/storageState, межу модуля (`module segment`) і план покриття.
2. **Runtime Simulation** (фаза B) — симуляція користувача з обмеженими можливостями (клавіатура, екранний читач, слабкозорий, reduced motion), відкриває всі попапи в межах модуля.
3. **Axe Scan** (фаза B) — axe-core: CLI на базовому стані + ін'єкція на кожному попапі (без `--fix`).
4. **Lighthouse Scan** (фаза B) — Lighthouse accessibility на базовому стані та доступних попапах.
5. **Web Review** (фаза B) — статичне ревʼю веб-коду за чек-листом `docs/wcag-2.2-checklist.md` (без браузера; поведінкові перевірки роблять етапи 2–4).
6. **Documents Review** (фаза B) — ревʼю офісних документів і PDF/ePub (пропускається, якщо документів немає).
7. **Markdown Review** (фаза B) — ревʼю markdown (пропускається, якщо .md немає).
8. **Consolidation** (фаза C) — обʼєднання, дедуплікація, severity scoring.
9. **Bug Reports** (фаза C, опційний) — експорт структурованих баг-репортів у файл `output/09-bug-reports.md`.
10. **Report** (фаза C) — фінальний звіт із пріоритезованими рекомендаціями (та переліком баг-репортів, якщо етап 9 виконаний).
11. **Verify** (фаза D) — обовʼязкова фінальна перевірка цілісності (не виправляє, лише фіксує).

## Крок 4. Перегляд журналу, звіту перевірки та архіву

- **Журнал виконання**: `output/pipeline-journal.md` — усі питання, відповіді, проблеми, рішення з timestamp.
- **Фінальний звіт аудиту**: `output/10-audit-report.md` — знахідки за серйозністю та план рекомендацій.
- **Баг-репорти** (якщо виконано етап 9): `output/09-bug-reports.md`.
- **Звіт перевірки**: `output/11-verification-report.md` — статус `PASSED` / `PASSED WITH WARNINGS` / `FAILED`.
- **Архів виконання**: `result_history/Pipeline_<дата-час запуску, UTC>/` — копія всіх артефактів цього запуску + `run-context.md` (параметри, статуси етапів за фазами, підсумок аудиту, перелік файлів). Створюється на етапі 11 командою `node tools/pipeline-state.mjs archive`, яка виключає файли сесій (`*storage*state*.json`, `*session*state*.json`, `*.session.json`). Попередній перегляд: `archive --dry-run`.
- **Усі часові мітки** у стані й журналі ставить `tools/pipeline-state.mjs` за реальним годинником (UTC, ISO 8601); вручну їх не пишуть.

## Крок 5. Відновлення після зупинки

Якщо пайплайн було зупинено, знову активуй оркестратор. Якщо у `pipeline-state.json` статус `stopped` або `running`, він покаже прогрес (за фазами A/B/C/D) і запропонує продовжити з поточної фази або перезапустити з фази A.

## FAQ

**Чи може пайплайн виправити знайдені проблеми?**
Ні. Це read-only пайплайн: він фіксує проблеми та дає рекомендації, але не редагує код чи документи. Виправлення виконує команда вручну.

**Куди пишуться результати?**
У теку `output/` (поточний запуск) та `result_history/` (архів завершених запусків). Жодних змін поза ними.

**Де шукати результати минулих запусків?**
Кожен завершений запуск архівується на етапі 11 у `result_history/Pipeline_<дата-час запуску>/` — там повна копія `output/` того запуску плюс `run-context.md` з контекстом. Мітка в назві папки — це час запуску пайплайну, тож запуски не перезаписують одне одного. Оригінали в `output/` лишаються (архівування копіює, не переміщує).

**Що як немає документів або markdown?**
Відповідні етапи (6 і/або 7) пропускаються — вручну (обери «Пропустити») або автоматично, якщо етап 1 не знайшов такого контенту.

**Який стандарт застосовується?**
WCAG 2.2 AA за замовчуванням. Правила — у skill `skills/a11y-rules.md`.

**Ціль аудиту — репозиторій у GitLab або GitHub. Як його підключити?**
Налаштуй відповідний MCP у `.vscode/mcp.json` за шаблоном `docs/mcp.example.json`: GitLab MCP (`@modelcontextprotocol/server-gitlab`) або GitHub MCP (`@modelcontextprotocol/server-github`). Етап 1 (Discovery) через читальні дії знайде репозиторій, обере гілку, перевірить SHA коміту і зчитає дерево файлів для інвентаризації, а етап 5 (Web Review) прочитає файли за SHA коміту. Використовується лише читання — пайплайн нічого не пише у репозиторій і не клонує його.

**Як виконується runtime-перевірка сторінки?**
Через Playwright MCP (`@playwright/mcp`, <https://github.com/microsoft/playwright-mcp>): етап 2 відкриває URL, симулює користувача з обмеженими можливостями і знімає accessibility-снапшоти всіх попапів у межах модуля; етапи 3 і 4 прогонять на тих же станах axe-core і Lighthouse. Це не змінює контент сторінки.

**Ціль за авторизацією — як відкрити захищені сторінки?**
Для цього кроку агент самостійно відкриває окремий браузер за допомогою **Playwright MCP** (`browser_navigate` на `<URL>`): користувач вручну проходить авторизацію (Basic Auth та/або логін на формі) у відкритому вікні браузера Playwright MCP і повідомляє «готово», після чого агент через `browser_run_code` зберігає лише отриманий `storageState` у `auth/playwright/.auth/<роль>.json` (резервний CLI-спосіб — `node tools/auth-login.mjs --role <роль> --url "<URL>" --wait-for-enter`). Перевірка стану виконується командою `node tools/auth-check.mjs --role <роль> --url "<URL>"`. Повний порядок — у файлі **`auth/AUTH-SETUP.md`**. Збережені стани лежать у `auth/playwright/.auth/<роль>.json` і не потрапляють у git. На етапі 1 (Discovery) вкажи, що ціль за авторизацією, і яку назву ролі використати.

**Чому знахідки мають однаковий формат?**
Єдиний структурований формат (severity, wcag, domain, source, location, issue, impact, recommendation, confidence) дозволяє дедуплікацію на етапі 8 і traceability до фінального звіту.

**Чи потрібен інтернет/сервер для сканерів?**
Для runtime-етапів (2 симуляція, 3 axe-core, 4 Lighthouse) потрібен доступний URL. Якщо URL немає — вони зафіксують обмеження, а перевірка коду (етапи 5–7) все одно виконається.

**Чому етапи 2–7 запускаються разом?**
Вони незалежні (кожен читає лише scope з етапу 1) і об'єднані у паралельну фазу B для економії часу. Барʼєр перед фазою C гарантує, що консолідація (етап 8) почнеться лише після завершення всіх обраних етапів фази B. Підтвердження для всієї групи — одне спільне.

**Чому runtime-перевірка розбита на три окремі етапи (2, 3, 4)?**
Симуляція користувача (клавіатура/екранний читач/слабкозорий/reduced motion), axe-core і Lighthouse — різні за природою перевірки з різними інструментами й форматом результату. Розділення дозволяє пропустити чи повторити лише одну з них без переробки решти, а оркестратор все одно показує по них одне спільне ревʼю в межах фази B.

**Чому runtime-етапи не натискають усі кнопки підряд?**
У веб-застосунках дії типу "Підписати", "Надіслати", "Видалити", "Підтвердити" змінюють реальні дані чи бізнес-процеси. Пайплайн — read-only, тож такі елементи фіксуються, але не натискаються автоматично; оркестратор запитає тебе окремо по кожному елементу, перш ніж дозволити один клік.

**Що, якщо один з паралельних етапів впаде?**
Інші етапи фази B продовжать роботу. Після барʼєра оркестратор покаже, який етап `failed`, і запитає: продовжити з наявними результатами чи зупинитись. Автоматично нічого не втрачається — рішення за тобою.
