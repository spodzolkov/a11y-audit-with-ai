# Правила аудиту доступності (WCAG 2.2 AA)

Цей skill містить правила предметної області для всіх агентів-етапів пайплайну аудиту доступності. Агенти посилаються на цей skill замість дублювання правил.

Цільовий стандарт: **WCAG 2.2 AA**.

## Повний чек-лист WCAG 2.2

Повний перелік критеріїв успіху (SC) рівнів A/AA з точними посиланнями на специфікацію, пояснення (Understanding) і прикладами виправлень для кожного критерію — **`docs/wcag-2.2-checklist.md`**. Усі агенти-етапи (02–07) мають посилатись на конкретний пункт цього файлу через поле `checklistRef` у знахідці, а не переказувати критерій своїми словами.

## Read-only принцип (не порушувати)

- Агенти НЕ змінюють код/документи, що аудіюються.
- Кожна знахідка містить рекомендацію «як виправити», але виправлення виконує людина, а не пайплайн.
- Запис на диск дозволено ТІЛЬКИ в `output/` (і `result_history/` на етапі 11).
- Запис у зовнішні системи повністю відсутній (опційний етап 9 лише експортує структуровані баг-репорти у `output/09-bug-reports.md`).

## Рівні серйозності (єдина шкала)

Використовуй ці чотири рівні консистентно у ВСІХ знахідках, звітах і CSV (узгоджено з axe-core):

| Рівень | Значення | Дія |
|--------|----------|-----|
| `critical` | Блокує доступ. Користувач AT не може виконати задачу чи отримати контент. | Виправити до релізу |
| `serious` | Погіршує досвід. Функція працює, але помітно складніша/заплутана. | Виправити до релізу |
| `moderate` | Неповно. Працює, але порушує best practice. | Виправити за можливості |
| `minor` | Є куди покращити. Працює коректно. | Виправити за можливості |

## Формат структурованої знахідки (обовʼязковий)

Кожна знахідка ВСІХ агентів має містити всі поля:

```
- id: <FINDING-NNN>
- severity: critical | serious | moderate | minor
- wcag: <SC номер і назва, напр. 1.4.3 Contrast (Minimum)>
- checklistRef: <номер SC у docs/wcag-2.2-checklist.md, напр. 1.4.3>
- domain: web | document | markdown
- source: <агент/сканер, що виявив>
- location: <шлях файлу:рядок або URL + селектор>
- issue: <що не так>
- impact: <вплив на користувачів AT / скрінрідера>
- recommendation: <як виправити (для людини, не автоматично)>
- confidence: high | medium | low
```

Не подавай знахідки суцільним текстом — тільки структуровано.

## Severity scoring (модель v2)

Для консолідованого зведення рахуй ваги:
- `critical` = 10, `serious` = 6, `moderate` = 3, `minor` = 1.

Метрики звіту:
- **Total findings** — кількість знахідок у межах цільового стандарту (WCAG 2.2 A/AA).
- **Weighted score** — сума ваг знахідок у межах цільового стандарту (чим більше, тим гірше).

### Поза цільовим стандартом
Знахідки рівня AAA (напр. 2.3.3 Animation from Interactions) і best practice без SC рівня A/AA (axe-теги `best-practice` без `wcag2a`/`wcag2aa`/`wcag21a`/`wcag21aa`/`wcag22aa`):
- зберігаються в консолідації в окремій секції `## Поза цільовим стандартом` (з тим самим форматом і id `FINDING-NNN`);
- НЕ входять у Total findings, Weighted score, розподіли і A11y health;
- не перетворюються на баги на етапі 9;
- у звіті 10 перелічуються окремим розділом «Рекомендації поза WCAG 2.2 AA».
`tools/verify-run.mjs` попереджає, якщо AAA-знахідка лишилась в основному переліку.

### Калібрування severity для автоматичних сканерів
Impact axe-core (і аудиту Lighthouse, який спирається на те саме axe-правило) — стартова точка, остаточний рівень визначається за впливом на задачу в модулі (intent-first):

| impact axe | Severity пайплайну за замовчуванням | Підвищити до | Знизити до |
|------------|--------------------------------------|--------------|------------|
| critical | critical | — | serious, якщо елемент не на ключовому шляху задачі модуля і є робоча альтернатива |
| serious | serious | critical, якщо runtime-етап підтвердив, що задачу неможливо виконати з AT/клавіатурою | moderate, якщо порушення лише в декоративній/неінтерактивній частині |
| moderate | moderate | serious, якщо елемент на ключовому шляху задачі | minor |
| minor | minor | moderate | — |
| `incomplete` (needs review) | не знахідка | — | — |

- `incomplete` стає знахідкою лише після підтвердження іншим етапом (runtime чи статика); до того — `Обмеження` або `confidence: low`.
- Будь-яке відхилення від рівня за замовчуванням фіксується в знахідці полем `severityRationale` (одне речення).
- Для однієї знахідки з кількох джерел береться найвищий обґрунтований рівень.
- **A11y health** — якісний підсумок: `FAIL` (є хоча б один critical), `AT RISK` (є serious, немає critical), `NEEDS WORK` (лише moderate/minor), `PASS` (0 знахідок).

## Дедуплікація

Якщо ту саму проблему виявили різні джерела (напр. axe-core і web review) — обʼєднати в одну знахідку, лишити найдетальнішу локацію, `confidence: high`, у `source` перелічити всі джерела.

## Веб — не-негоційовані стандарти

### Semantic HTML First
- Нативні елементи перед ARIA: `<button>` а не `<div role="button">`, `<nav>/<main>/<header>/<footer>` для лендмарків.

### Heading Structure
- Один H1 на сторінку. Не пропускати рівні (H1→H2→H3). Рівень заголовка не обирати за візуалом.

### Buttons vs Links
- `<button>` для дій, `<a href>` для навігації. Не вкладати одне в інше.

### Images / Icons
- Значущі зображення — описовий `alt`; декоративні — `alt=""` + `aria-hidden="true"`.
- Іконки-кнопки — `aria-label`; декоративні іконки поряд з текстом — `aria-hidden="true"`.

### Forms
- Кожен input має label; помилки повʼязані через `aria-describedby`; фокус на першу помилку; required позначено; повідомлення не лише кольором.

### Interaction / Focus
- Усі інтерактивні елементи досяжні клавіатурою; порядок табуляції відповідає візуалу; без позитивного `tabindex`; модалки трапують фокус і повертають його; Escape закриває оверлеї.

### ARIA
- Без надлишкового ARIA на семантичних елементах; стани оновлюються динамічно; усі `aria-controls/labelledby/describedby` посилаються на валідні ID; live-regions для динамічного контенту.

### Visual
- Контраст тексту WCAG AA: 4.5:1 (звичайний), 3:1 (великий); контраст UI-компонентів 3:1; видимий фокус з контрастом 3:1; інформація не лише кольором; підтримка `prefers-reduced-motion`.

### Links
- Описовий текст (не «клікніть тут»); візуально відрізняються не лише кольором; повторюваний текст лінків диференційований; попередження про відкриття в новій вкладці.

### Page Setup
- `<html lang>` завжди; описовий `<title>`; коректний viewport для зуму; skip-link на основний контент.

### WCAG 2.2 нові критерії (перевіряти окремо)
- 2.4.11 Focus Not Obscured (Minimum), 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum, 24×24), 3.2.6 Consistent Help, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication (Minimum).

## Документи — стандарти

### Спільне
- Заголовок документа (title/metadata), мова, логічна структура заголовків, alt-текст для зображень, описові гіперлінки, читабельний порядок.

### Word (.docx)
- Стилі заголовків (не «жирний текст» замість Heading), alt для зображень, заголовки таблиць, описові лінки, мова документа.

### Excel (.xlsx)
- Осмислені назви аркушів, іменовані таблиці з заголовками, alt для графіків/зображень, уникати обʼєднаних клітин, які ламають навігацію.

### PowerPoint (.pptx)
- Унікальні заголовки слайдів, alt-текст, коректний порядок читання, підписи/транскрипти медіа.

### PDF (PDF/UA-1)
- Тегована структура, порядок читання, alt-текст, мова, доступні форми, закладки для довгих документів (Matterhorn Protocol як довідник).

### ePub
- Семантична розмітка, навігаційний зміст (nav), мова, alt-текст, порядок читання.

## Markdown — стандарти

- Один H1 на документ; послідовна ієрархія заголовків без пропусків.
- Alt-текст для зображень `![alt](src)`.
- Описовий текст посилань (не «тут»/«читати далі»).
- Таблиці з рядком-заголовком.
- Списки коректно розмічені; блоки коду з мовним тегом.
- Немає порожніх заголовків; немає заголовків, обраних лише за візуальним розміром.
- Перевірка сумісна з правилами markdownlint.

## Intent-first (важливо)

Перед тим як позначити нестандартний ARIA чи незвичний патерн проблемою — врахуй, чи він працює з реальним AT. Якщо працює зі скрінрідером і питання лише в «чистоті» специфікації — познач як `minor` і поясни компроміс. Не пропонувати змін для нульової користі користувачу.
