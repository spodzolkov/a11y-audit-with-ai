# WCAG Bug Report Generator (пайплайн a11y-audit-pipeline)

Skill для етапу 9 (`A11y Bug Reports`): перетворює консолідовані знахідки (`output/08-consolidation.md`) на готові структуровані баг-репорти та експортує їх у файл `output/09-bug-reports.md`.

Мова репортів: **українська**. Критерії WCAG, посилання на specification/Understanding і приклади виправлень беруться **виключно** з `docs/wcag-2.2-checklist.md` за `checklistRef` знахідки, а не з пам'яті.

---

## 1. Вхідні дані

Усі дані для генерації баг-репортів беруться з наявних артефактів пайплайну (нічого не вигадувати):
- тестовий URL, роль і `module segment` — з `output/01-discovery.md`;
- оточення (розділ 4) — з `output/02-runtime-simulation.md`, `output/03-axe-scan.md`, `output/04-lighthouse-scan.md`;
- консолідовані знахідки, severity і WCAG — з `output/08-consolidation.md`;
- опис правил, посилання та приклади виправлення — з `docs/wcag-2.2-checklist.md`.

Якщо у `01-discovery.md` не вказано людську назву модуля, використовуй `module segment` (або запитай назву модуля у людини лише за потреби).

---

## 2. Гранулярність: що саме перетворюється на баг-репорт

| Severity знахідки | Правило |
|-------------------|---------|
| `critical`, `serious` | Один баг-репорт на кожну консолідовану знахідку (`FINDING-NNN`). |
| `moderate`, `minor` | Групувати: один баг-репорт на кожен критерій WCAG (`checklistRef`), у Description перелічити всі знахідки групи (id, локація, стан) окремим списком. Якщо у групі знахідки з різних модулів/доменів, розбий на кілька груп. |

Кожен баг-репорт має поле `findings: [FINDING-NNN, ...]` для traceability у `output/09-bug-reports.md`.

---

## 3. Мапінг severity: пайплайн -> S1..S5

| Severity пайплайну | Рівень у Summary |
|--------------------|------------------|
| `critical` | `S2` |
| `serious` | `S3` |
| `moderate` | `S4` |
| `minor` | `S5` |

`S1` (блокуючий) ставить лише людина (за запитом під час ревʼю етапу). Для групи береться найвища severity у групі.

---

## 4. Оточення (чесно, без вигадок)

У секції "Оточення" використовуй лише те, що є в артефактах етапів 1–4:

- **Тестові URL**: з Discovery (або локальний шлях/репозиторій, якщо перевірявся лише код).
- **ОС / Браузер**: з артефактів Playwright (етап 2). Якщо там не зафіксовано точну версію, пиши "не зафіксовано артефактами етапу 2" замість вигаданої.
- **Допоміжна технологія**: рівно така формула, без реального скрінрідера:
  `accessibility-снапшот Playwright (без реального скрінрідера); axe-core <версія з 03>; Lighthouse <версія з 04>`.
  Якщо етап 2, 3 або 4 був `skipped`, відповідний інструмент не згадується (для суто статичного аналізу вкажи `статичний аналіз коду / документів`).
- **Роль користувача**: роль storageState з Discovery (без секретів).

НЕ пиши NVDA/JAWS/VoiceOver, якщо їх не використовували.

---

## 5. Формат Summary та Description

### Summary
```
[S{n}] (Модуль / A11y) Короткий опис проблеми доступності [WCAG {номери критеріїв}]
```
Модуль береться з Discovery (назва модуля) або з `module segment`, якщо назви немає. Для групи: опис узагальнює критерій, напр. `... [WCAG 2.5.8]`.

### Description (РІВНО ці секції)
```
**Оточення:**

Тестові URL:
{url}

ОС: {ос}

Браузер: {браузер}

Допоміжна технологія: {за розділом 4}


**Дані для відтворення:**

• {передумова 1: роль, стан сторінки, відкритий попап}
• {передумова 2}


**Кроки відтворення:**

1. {крок 1}
2. {крок 2}


**Фактичний результат:**

Опис проблеми:
{чіткий опис недоступності та впливу на користувача}

Порушені пункти WCAG 2.2:
• {SC} {назва} (Рівень {A/AA})
  Опис правила: {суть критерію з чек-листа}
  Посилання: https://www.w3.org/TR/WCAG22/#{slug}
  Пояснення: https://www.w3.org/WAI/WCAG22/Understanding/{slug}.html

Знахідки пайплайну: {FINDING-NNN, ...} (джерела: {RUN/AXE/LH/WEB ...})


**Очікуваний результат:**

{як має поводитися елемент, щоб відповідати критерію}

Запропоноване рішення:
{кроки виправлення з чек-листа}

Приклад (best practice):
{короткий приклад з розділу "Виправлення" відповідного SC чек-листа}
```

Правила:
- Секції називаються рівно так, жирним.
- У "Фактичному результаті" обовʼязково: опис проблеми, номер(и) SC, опис правила, посилання на specification та Understanding (slug з чек-листа).
- В "Очікуваному результаті" обовʼязково: рішення + приклад best practice (з чек-листа; за потреби адаптуй до конкретного селектора/компонента з локації знахідки).
- Не приписуй критерії "про всяк випадок": лише ті, що в `wcag`/`checklistRef` знахідки.
- Критерії рівня AAA та best practice поза цільовим стандартом у баг-репорти не включай.
- Для знахідок, які потребують пояснення про стан попапа, вказуй `state` (напр. `popup:Додати договір`) у кроках відтворення.

## 6. Вихідний файл `output/09-bug-reports.md`

```
# Етап 9 — Bug Reports

## Параметри
- Модуль / Ціль: <назва або шлях/URL>
- Стандарт: WCAG 2.2 AA
- Усього баг-репортів: <N>

## Зведення
| № | Summary | S | SC | Findings |
|---|---------|---|----|----------|
| BUG-001 | [S2] (Модуль / A11y) ... [WCAG 4.1.2] | S2 | 4.1.2 | FINDING-001 |

## Баг-репорти
### BUG-001
findings: [FINDING-001]
Summary:
[S2] (Модуль / A11y) ... [WCAG 4.1.2]
Description:
...
```

Усі баг-репорти пронумеровані `BUG-NNN` (ідентифікатор пайплайну) та містять прив'язку до `FINDING-NNN` у таблиці «Зведення» і в полі `findings`.
