# Етап 5 — Web Review (статичне ревʼю коду веб)

## Мета
Провести детальне ручне ревʼю ВИХІДНОГО КОДУ (HTML/JSX/CSS/React/Vue/Angular/Svelte/vanilla) за доменами доступності WCAG 2.2 AA, які видно у статичному тексті файлів, без запуску сторінки в браузері. Тільки виявлення проблем і рекомендації — без редагування коду.

Межа відповідальності: усе, що потребує реального рендеру, взаємодії користувача чи браузера (поведінка клавіатури/фокусу, трап фокусу в модалках, реакція на Escape, анонси live-regions, обчислений контраст, reflow/масштабування, reduced motion, обхід попапів) належить ЛИШЕ етапам 2 (Runtime Simulation), 3 (Axe Scan), 4 (Lighthouse Scan). Цей етап їх НЕ дублює і НЕ використовує Playwright/браузер.

## Вхідні дані
- `output/01-discovery.md` — веб-файли, фреймворк.
- Чек-лист: `docs/wcag-2.2-checklist.md` (повний перелік критеріїв WCAG 2.2 AA з посиланнями та прикладами виправлень) — основне джерело критеріїв для цього етапу.

> Цей етап належить до паралельної фази B і виконується одночасно з етапами 2–4, 6, 7. Він читає ЛИШЕ scope з етапу 1 і НЕ залежить від виходів інших етапів. Кореляція/дедуплікація з runtime-знахідками (етапи 2–4) робиться пізніше на етапі 8.

## Інструменти
- Локальна ціль: `read_file` / `read_code`, `grep_search`, `list_directory`.
- **Ціль у GitLab** (коли код у віддаленому репозиторії GitLab): ЛИШЕ GitLab MCP `gitlab_read`. Клонувати репозиторій чи зберігати копії вихідних файлів (у `%TEMP%`, `output/` чи деінде) ЗАБОРОНЕНО.
  - Інвентар файлів: `gitlab_read tree` з `ref` = **SHA коміту** з Discovery (не назва гілки), `recursive: true`, по теках модуля і бібліотек, які він імпортує.
  - Пакетне читання: `gitlab_read graphql` з запитом
    ```graphql
    query($p: ID!, $ref: String!, $paths: [String!]!) {
      project(fullPath: $p) { repository { blobs(ref: $ref, paths: $paths) { nodes { path size rawTextBlob } } } }
    }
    ```
    пакетами по 20–30 шляхів. Відсутні шляхи API мовчки пропускає: порівнюй повернені `path` із запитаними і фіксуй різницю як "не прочитано".
  - `gitlab_read file` — лише для поодиноких файлів або якщо blob у пакеті завеликий/обрізаний.
- **Ціль у GitHub** (коли код у віддаленому репозиторії GitHub): ЛИШЕ читальні інструменти GitHub MCP (`@modelcontextprotocol/server-github`). Клонувати репозиторій чи зберігати копії вихідних файлів (у `%TEMP%`, `output/` чи деінде) ЗАБОРОНЕНО; жодних write-дій (`create_or_update_file`, `push_files`, `create_pull_request`, `create_branch` заборонені).
  - Інвентар файлів: `get_file_contents` по директоріях модуля та бібліотек із `branch` = **SHA коміту** з Discovery (або `search_code` у межах `repo:owner/repo`).
  - Читання файлів: `get_file_contents` із `owner`, `repo`, `path` та `branch` = **SHA коміту** з Discovery, групами по 20–30 файлів із проміжним записом прогресу. Непрочитані файли фіксуй у секції «Покриття».

Жодних Playwright MCP, `browser_*`, навігації чи виконання коду в браузері на цьому етапі — усе статично, за текстом файлів.

## Покриття (обовʼязково для GitLab / GitHub-цілі)
1. **Scope модуля**: усі шаблони (`*.html`, inline `template:` у `*.ts`), стилі (`*.scss`/`*.css`) і компоненти модуля з Discovery (напр. `apps/orders/**`).
2. **Бібліотечні компоненти**: компоненти з `libs/**`, які модуль імпортує (за `import ... from '@.../shared-...'` у `*.ts` модуля і селекторами в шаблонах). Глибина — один рівень імпорту; глибше — у `Обмеження`.
3. **Метрика**: `Прочитано N із M файлів scope` окремо для модуля і для `libs/`. Неповне покриття (N < M) — не підстава вигадувати результат: непрочитані файли перелічуються.
4. **Проміжний запис**: після кожного пакета дописуй знахідки й прогрес у `output/runtime/05/progress.md` (номер пакета, шляхи, кількість знахідок). Якщо сесію перервано, продовжуй з наступного пакета, а не з початку.

## Домени перевірки (статичний аналіз коду)
1. **Структура/семантика**: один H1 на шаблон/сторінку, ієрархія заголовків у розмітці, лендмарки (`<nav>/<main>/<header>/<footer>`), `<html lang>`, `<title>`, наявність skip-link у розмітці, `alt`-атрибути, обробка іконок (`aria-hidden`/`aria-label`).
2. **ARIA (статично)**: відсутність надлишкового ARIA на семантичних елементах, валідні/існуючі ID у `aria-controls/labelledby/describedby` (перевіряється по тексту файлів), коректні ролі, відсутність ARIA на елементах, де вона суперечить семантиці.
3. **Фокус/клавіатура (лише те, що видно в коді)**: наявність `tabindex` (особливо позитивного — проблема), `onClick` без відповідного `onKeyDown`/`role`/`tabIndex`, елементи-псевдокнопки (`<div onClick>`), відсутність видимого `:focus`/`:focus-visible` стилю в CSS.
4. **Форми**: `label`/`for` або `aria-label` для кожного `input`, `aria-describedby` для помилок, `required`/`aria-required`, чи повідомлення про помилку не кодується лише кольором (перевірка класів/стилів).
5. **Контраст/візуал (за значеннями в коді)**: кольори тексту й фону з CSS/токенів/теми — обчисли контраст за формулою WCAG там, де обидва кольори відомі статично; позначай як `confidence: low/medium`, якщо колір обчислюється динамічно (runtime-перевірку залишай етапам 2–4).
6. **Live-regions (статично)**: наявність `aria-live`/`role="status"|"alert"` у розмітці динамічних ділянок (тости, лоадери) — лише перевірка наявності атрибута в коді, не поведінки.
7. **Лінки**: текст посилання в розмітці (не «тут»/«читати далі»), `target="_blank"` без попередження в тексті/aria-label.
8. **Таблиці**: `scope`, `<caption>`, `<th>`/`headers` у розмітці.
9. **Форми/автентифікація (статично)**: ознаки `autocomplete`, дублювання введення тих самих даних у формі (3.3.7), наявність альтернатив captcha/аутентифікації без когнітивного тесту (3.3.8) — якщо видно з коду.
10. **WCAG 2.2 нове, що перевіряється статично**: 2.5.8 Target Size (мінімальні розміри кліку в CSS/стилях кнопок), 3.2.6 Consistent Help (наявність і позиція елемента допомоги в шаблоні), 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication (Minimum) — за кодом форм.

Повний перелік критеріїв, формулювання і приклади виправлень — `docs/wcag-2.2-checklist.md`. Критерії 2.4.11 (Focus Not Obscured), 2.5.7 (Dragging), реальна поведінка фокусу/клавіатури й контраст обчисленого стилю НЕ перевіряються тут: у чек-лісті вони позначені як "runtime" і закриваються етапами 2–4.

Врахуй фреймворк-специфіку (React aria-* camelCase, Vue v-if/live-region, Angular [attr.aria-*]/LiveAnnouncer, Svelte transitions/reduced-motion) — як вона виглядає в коді.

## Алгоритм виконання
1. Якщо у scope немає веб-контенту — оркестратор пропускає етап (`skipped`).
1a. Віддалена ціль (GitLab або GitHub): побудуй перелік файлів scope (розділ «Покриття»), прочитай їх пакетами за SHA коміту (`graphql repository.blobs` для GitLab або `get_file_contents` для GitHub), після кожного пакета — проміжний запис у `output/runtime/05/progress.md`.
1b. Застосуй правила R01–R14 до кожного прочитаного файлу.
2. Для кожного критерію чек-листа `docs/wcag-2.2-checklist.md`, позначеного як "статично перевірюваний", пройди файли scope (`read_code`/`grep_search` локально або прочитаний вміст файлів для GitLab / GitHub).
3. Для кожної проблеми сформуй структуровану знахідку (skill `#Accessibility Audit Rules`), з посиланням на конкретний пункт чек-листа (`wcag` + `checklistRef`).
4. Застосуй intent-first: нестандартні, але коректно розмічені для AT патерни не завищувати за серйозністю.
5. Якщо критерій вимагає рендеру/поведінки (runtime) — НЕ намагайся його перевірити тут; залиш порожнім або познач `see: етап 2/3/4`.

(Дедуплікація з runtime-знахідками виконується на етапі 8, коли доступні всі виходи фази B.)
