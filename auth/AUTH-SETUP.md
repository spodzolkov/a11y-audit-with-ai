# AUTH-SETUP — Ручна авторизація через браузер зі збереженням сесії

Ця інструкція описує, як отримати та зберегти авторизований стан сесії (**storageState**) для цілей аудиту, доступних лише після логіну.

Авторизація виконується **вручну людиною через браузер**, а пайплайн зберігає **лише отриманий стан сесії** (`cookies` та `localStorage`) у файл `auth/playwright/.auth/<роль>.json`. Пайплайн не приймає, не зберігає і не обробляє паролі, логіни чи ключі.

> Стосується етапів 2 (Runtime Simulation), 3 (Axe Scan) і 4 (Lighthouse Scan), коли ціль за автентифікацією. Перевірку стану робить етап 1 (Discovery) та кожен runtime-етап перед стартом.

## Як це влаштовано

- **Playwright MCP (основний спосіб)** — коли на етапі 1 (Discovery) або перед runtime-етапами 2–4 сесія відсутня чи прострочена (`missing` / `expired`), **агент самостійно відкриває окремий браузер за допомогою Playwright MCP** (`browser_navigate` на `<URL цілі>`). Користувач вручну проходить авторизацію (включно з HTTP Basic Auth та формою логіну на сторінці) у відкритому вікні браузера Playwright MCP і повідомляє «готово». Після цього агент через `browser_run_code` зберігає отриманий `storageState` у `auth/playwright/.auth/<роль>.json` (`await page.context().storageState({ path: 'auth/playwright/.auth/<роль>.json' })`), залишаючи браузер Playwright MCP відкритим для подальших runtime-перевірок.
- **`tools/auth-login.mjs` (резервний CLI-інструмент)** — відкриває видиме вікно браузера Chromium (Playwright з `tools/`) на цільовому URL, чекає, поки користувач увійде в систему вручну, після чого зберігає лише `storageState` у `auth/playwright/.auth/<роль>.json` і закриває браузер.
- **`tools/auth-check.mjs`** — перевіряє у фоновому режимі (`headless`), що збережений файл `auth/playwright/.auth/<роль>.json` існує і відкриває цільовий URL без редіректу на сторінку логіну.
- Файли стану `auth/playwright/.auth/<роль>.json` — **секрет** (живі токени сесії): вони ігноруються git (`auth/**/*.json`, `auth/playwright/`), ніколи не копіюються в `output/` чи `result_history/`, а їхній вміст не логується.

## Назва ролі (`<роль>`)

Ім'я ролі використовується як ідентифікатор файлу сесії (`auth/playwright/.auth/<роль>.json`), наприклад: `director`, `accountant`, `fop`, `viewer` або `default`. Для повного обходу модуля обирай обліковий запис із потрібними правами доступу до сторінки.

## Порядок авторизації (отримання та збереження сесії)

Усі команди виконуються з кореня проєкту.

1. Переконайся, що залежності `tools/` встановлені (один раз):
   ```powershell
   npm install --prefix tools
   ```
2. Запусти скрипт ручної авторизації для потрібної ролі та URL цілі:
   ```powershell
   node tools/auth-login.mjs --role <роль> --url "<URL цілі>"
   ```
   - Відкриється вікно браузера Chromium з переходом на `<URL цілі>`.
   - Пройди авторизацію вручну у вікні браузера.
   - Щойно браузер повернеться з хоста авторизації на цільовий сайт і завантажить сторінку, скрипт автоматично збереже стан сесії у `auth/playwright/.auth/<роль>.json` і закриє вікно.
   - Якщо потрібно вручну контролювати момент збереження (наприклад, коли логін відбувається на тому самому домені без редіректу на SSO), додай прапорець `--wait-for-enter` і натисни `Enter` у терміналі після завершення входу:
     ```powershell
     node tools/auth-login.mjs --role <роль> --url "<URL цілі>" --wait-for-enter
     ```
3. Перевір збережену сесію:
   ```powershell
   node tools/auth-check.mjs --role <роль> --url "<URL цілі>"
   ```
   Очікуваний результат — `valid` (код 0). `missing` (3) — файлу немає; `expired` (4) — сторінка редіректить на логін; `error` (5) — помилка мережі чи браузера. Скрипт виводить вік файлу (`ageMinutes`) і найближчий термін дії cookie (`earliestCookieExpiryMinutes`), але не вміст стану.
4. Передай шлях до стану в конфігурацію Playwright MCP (`.vscode/mcp.json`) і перезапусти (reconnect) сервер MCP.

## Налаштування Playwright MCP

`--storage-state` у `@playwright/mcp` використовується разом із `--isolated`. Фрагмент `.vscode/mcp.json` (повний шаблон — `docs/mcp.example.json`):

```json
"playwright-mcp": {
  "type": "stdio",
  "command": "npx",
  "args": [
    "-y",
    "@playwright/mcp",
    "--isolated",
    "--storage-state", "auth/playwright/.auth/<роль>.json",
    "--output-dir", "output/runtime/mcp",
    "--output-mode", "file"
  ]
}
```

- Шляхи відносні до кореня проєкту: VS Code запускає workspace-сервер з робочою текою = корінь воркспейсу. У глобальних налаштуваннях MCP користувача використовуй абсолютні шляхи з прямими слешами (`C:/...`).
- Пакет `@playwright/mcp` завантажується зі стандартного відкритого реєстру npm (`https://registry.npmjs.org/`).
- `--save-session` заборонено: він пише сесію у файл поза `auth/`.
- Після кожного оновлення сесії (`auth-login.mjs`) перезапусти (restart/reconnect) Playwright MCP у VS Code, щоб сервер підхопив новий файл стану.

## Термін дії та оновлення сесії

Серверна сесія має обмежений час життя (зазвичай ~30 хвилин). Тому перед runtime-фазою (і щоразу, коли `auth-check` повертає `expired`) онови сесію:

```powershell
node tools/auth-login.mjs --role <роль> --url "<URL цілі>"
node tools/auth-check.mjs --role <роль> --url "<URL цілі>"
```

і зроби reconnect Playwright MCP у VS Code.

## Безпека (обовʼязково)

- `auth/playwright/.auth/*.json` — секрет (живі токени сесії): не копіювати в `output/` чи `result_history/`, не логувати вміст, не комітити в git, не редагувати вручну чи агентом. Перевірка: `git ls-files auth/playwright` має повертати порожній список.
- Паролі, логіни чи ключі не передаються в аргументах команд чи файлах конфігурації — користувач вводить їх виключно сам у вікні браузера під час виконання `auth-login.mjs`.

## Що вказати на етапі 1 (Discovery)

- Чи ціль за авторизацією (так/ні).
- Яку назву ролі (`<роль>`) використати для `auth/playwright/.auth/<роль>.json`.
